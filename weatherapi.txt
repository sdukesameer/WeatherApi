Thank you, I'd like to walk you through Skyline, a weather dashboard I built on top of the OpenWeather API. It shows current conditions, air quality, a sunrise-to-sunset tracker, and hourly and 5-day forecasts for any city the user searches, or for their current location.

I built it with plain HTML, CSS and JavaScript, deliberately without a framework, so I could focus on getting the fundamentals — DOM structure, state, and API composition — right. When a user searches, I call OpenWeather's Geocoding API to resolve the city name to a latitude/longitude pair, with a debounced autocomplete dropdown so results update as they type without hammering the API on every keystroke. Once I have coordinates, I fire the current weather, forecast, and air pollution requests together with Promise.allSettled rather than chaining them, since none of them depend on each other. I use allSettled rather than all deliberately: current conditions are required, but a failed air-quality call shouldn't stop the rest of the dashboard from rendering.

A few decisions I'd call out as the interesting engineering, rather than just wiring up an API:

First, cancellation. If someone searches twice quickly, the slower first response can land after the second and overwrite fresher data on screen. I hold an AbortController per request and abort the previous one whenever a new search starts, and the same controller carries a timeout, so a hanging request fails with a real message instead of leaving the skeleton up forever.

Second, units. I fetch everything in metric once and convert at render time, so switching between Celsius and Fahrenheit is a pure re-render — no second API call, no loading state. Imperial mode also switches wind to mph, visibility to miles and pressure to inches of mercury, rather than only relabelling the temperature.

Third, timezones, which is where this kind of app usually gets subtly wrong. Every city time is derived by shifting the UTC timestamp by that city's own offset and reading it back with the getUTC* methods, so the viewer's local timezone never leaks in. That matters for grouping the 3-hour forecast slots into calendar days: if you use the browser's timezone, users west of UTC see the day labels shifted by one.

Fourth, contrast. The UI reacts to the data — each condition maps to a theme key that tints a time-of-day palette, so the background gradient and glass tint shift with the real weather, and a canvas layer adds rain, snow, stars or lightning. The catch is that a background driven by live data can land anywhere from near-black to near-white, and white text on a bright midday sky is unreadable. So instead of hardcoding a text colour per condition, I compute the WCAG relative luminance of the generated gradient and flip a data attribute at 0.197 — the point where dark and light ink give equal contrast — and the glass panels carry a scrim so contrast depends on the panel rather than on today's weather. I verified every condition-and-time-of-day combination clears its contrast floor.

The sunrise-to-sunset widget is a small piece of maths I enjoyed: I compute how far through the day we are as a fraction and place a dot at that point along an SVG arc using getPointAtLength, so it's a genuine read of the time of day. Above the Arctic Circle the API can report sunrise and sunset as the same instant, which would divide by zero, so that case is detected and labelled polar day/night instead.

For the forecast, the free tier only returns 3-hour steps, so the daily view groups them by local calendar day and picks the slot closest to 1pm as that day's representative reading. Days at the edges of the window are partial, and I mark those rather than presenting a high and low computed from two readings as if it were the full day. Tapping any day expands it into its 3-hourly breakdown, and the hourly strip carries a temperature sparkline drawn from the measured positions of the cells so it stays aligned at any zoom level.

Finally, the parts that make it feel finished: saved places and recent searches in localStorage, the current city reflected in the URL so it can be shared or bookmarked, a service worker that caches the app shell, and the last successful payload replayed with a "cached" note if a request fails — so an offline user sees real data with an honest label instead of an empty screen. It auto-refreshes every ten minutes and when the tab regains focus.

The one limitation I'd flag honestly is the API key. It's in the client, because a static site with no backend cannot hide a key — anyone can read it from the JavaScript. The app lets you supply your own key at runtime instead, but the only real fix is a small backend that holds the key and proxies the requests, and that's what I'd build if this went past a portfolio piece.
